# moodbot-next

Микросервисы, добавленные к MoodBot в курсе **«Проект: Next Level»**
(DevopsTrain). Продолжение проекта из курса `12-factor-app`
(репозитории `users`, `telegram-api`, `scheduler`).

| Сервис | Что делает |
|---|---|
| `answers` | владелец истории ответов: потребитель Kafka → PostgreSQL + REST на чтение |
| `analytics` | потребитель Kafka → ClickHouse, агрегаты по динамике настроения |
| `web-admin` | внешний веб-кабинет пользователя (единственный сервис за Ingress) |
| `recommender` | персональные рекомендации через внешний LLM API |

## Почему монорепозиторий

Четыре сервиса одной команды, выкатываются вместе, делят контракт событий.
Практическая причина: self-hosted runner GitHub нельзя расшарить между
репозиториями личного аккаунта (runner group бывает только у организации) —
четыре репозитория означали бы четыре запущенных раннера.

Общий контракт событий при этом живёт **не здесь**, а в модуле
`github.com/Ivanvnew75/libs` (пакеты `events`, `kafkax`): продюсер
(`telegram-api`) лежит в другом репозитории, а пакеты под `internal/`
за пределы модуля не видны — это правило компилятора, а не соглашение.

## Сборка

Один Dockerfile на все сервисы, сервис выбирается аргументом:

```bash
docker build --build-arg SERVICE=answers -t ghcr.io/ivanvnew75/answers:0.1.1 .
```

## Схема БД

Каждый сервис владеет своей схемой в общей базе и имеет **свою роль**
PostgreSQL, у которой нет прав на чужие схемы. Миграции встроены
в бинарник (`embed`) и применяются подкомандой `migrate` из того же образа.
